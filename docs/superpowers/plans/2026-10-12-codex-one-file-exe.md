# Bodycam Diagnostics: ровно один EXE для пользователя

Согласованное требование владельца от 12 октября 2026. **Исполнитель реализации, компиляции и тестов: Codex, облачная среда `BodycamDiagnostics`.** Этот файл является постоянной инструкцией для следующих задач Codex: пользователь не должен каждый раз вспоминать установку зависимостей и последовательность запуска.

## Что должно получиться

**Один переносимый файл `BodycamDiagnostics.exe`.** Его скачивают и дважды щёлкают. Никаких ZIP с 20 файлами, PowerShell, CMD, отдельной установки PresentMon/FFmpeg, Python, DLL рядом с EXE, прав администратора или скачиваний в компьютерном клубе. Доступ к сети при запуске не требуется.

Для достижения этого допустимо **включить в ресурсы основного PE-файла** заведомо проверенные версии `PresentMon.exe`, `ffmpeg.exe`, `runtime-tools.sha256`, `СПРАВКА.txt` и другие обязательные данные. Существующие контроллеры запускают PresentMon/FFmpeg как дочерние процессы, поэтому фактическое создание инструментов на диске **неизбежно**: распаковывать их исключительно в отдельный каталог текущего пользователя `%LOCALAPPDATA%\BodycamDiagnostics\Runtime\<версия или SHA256 манифеста>\`, **прозрачно**, с понятной ошибкой при отказе. Ни в Windows/System32, ни в Program Files, ни в файлы Bodycam/Gizmo ничего не писать. Не использовать автоповышение привилегий, обход антивируса, скрытые драйверы, инъекции в игру или маскировку процессов.

### Границы совместимости

1. Не ломать работающий способ обычной сборки. Новый режим сборки `BODYCAM_SINGLE_EXE=ON` или аналог включается **отдельно**; старые тесты и режимы сохраняются.
2. Заимствовать SHA-256 **только из существующих** `runtime-tools.sha256` и `runtime-tools.sources.json`, доверенный якорь генерируется в `RuntimeToolTrustAnchor.h`. Проверять **каждый** скачанный файл во время сборки, затем проверять распакованные бинарники **перед запуском**, а также перед mux/finalization как сейчас. При несовпадении SHA отказывать без запуска. Никаких ослаблений `ToolPreflight`.
3. Для сборки в Linux использовать **LLVM-MinGW**; Python допустим только для build-time инструмента. Загружать зависимости в Codex, а не у конечного пользователя. Обеспечить статическое связывание необходимых компиляторных C/C++ runtime; после линковки исследовать PE import table и отвергнуть вариант, требующий `libc++.dll` / `libunwind.dll` рядом с EXE. Системные DLL Windows допустимы.
4. Сохранить F8/F9, новый интерфейс с верхней панелью, состояние записи и цветовую индикацию, Gizmo compatibility mode, журнал событий, отдельные записи `video_part_N`, отчёты и их копирование, защиту диагностических данных от удаления. Кнопка «Справка» должна работать даже без файлов рядом с EXE.
5. Полноэкранный UIAccess helper сейчас зависит от отдельной установленной подписанной программы; кросс-сборка LLVM-MinGW **не гарантирует UIAccess**. Не объявлять его работающим и не добавлять ненужную установку администратора. Допустима существующая деградация до встроенного оконного/Borderless HUD с диагностической записью о причине. Не обходить Gizmo.
6. Убедиться в условиях распространения конкретных бинарников FFmpeg и PresentMon, предоставить обязательные лицензии/уведомления/ссылки на исходники, если применимо, внутри приложения или через доступные сведения. Не заявлять публичный релиз, пока это не проверено.
7. Если рядом с EXE нет прав записи, сохранять сессии в пользовательском каталоге, но не терять отчёты. Показывать в интерфейсе их реальное расположение. Избегать случайной перезаписи записей и логов.

## Работа Codex

1. Начать с проверки **актуального HEAD**, исходников, `AGENTS.md` (если есть), состояния Git и текущих тестов; не перезаписывать изменения другого агента. Последняя известная точка до задачи: `6f75719` на `feature/recording-gizmo-help`.
2. Написать воспроизводимые build-time шаги для одного EXE, интеграционные тесты проверки SHA-256, idempotent per-user unpack, ошибочных и успешных сценариев, отсутствия админ-доступа и кросс-сборки. Логику и тесты модифицировать только в рабочей ветке.
3. Собрать Windows x64 `BodycamDiagnostics.exe` и тестовые PE-файлы в Codex. Если запуск Windows недоступен, честно отделить успешную **кросс-компиляцию** от **испытаний на Windows**.
4. Выполнить доступные Linux-тесты; учесть известные 5 успешных тестов Codex, не повторять без причины массивные стресс-прогоны. Запустить целевые проверки нового упаковочного кода, проверить ресурсы PE, SHA-256 и список внешних DLL.
5. Создать **только один пользовательский артефакт `BodycamDiagnostics.exe`**. Логи компиляции, test fixtures и технические файлы держать отдельно в workspace Codex, но не смешивать с пользовательским EXE. В отчёте указать SHA-256, размер, фактический путь артефакта и полный SHA коммита.
6. Если подготовить достоверный one-file EXE не удалось, **не подсовывать многокомпонентный ZIP под видом готового EXE**; точно описать блокер и оставить рабочие изменения изолированными.

## Абсолютные ограничения

- **GitHub Actions не запускать**. Включённые минуты исчерпаны; CI платный/недоступен.
- **Work не использовать**. Разработка/сборка/тесты только Codex.
- **main/stable не трогать**. Работать только с `feature/recording-gizmo-help`; PR #3 оставить Draft, не сливать.
- Никаких заявлений `СОБРАНО`, `ПРОВЕРЕНО`, `ПРОВЕРЕНО НА УСТРОЙСТВЕ` без реальных доказательств соответствующего этапа.
- Приоритет защиты данных и совместимости с компьютерным клубом выше эффектной упаковки. Самораспаковка может вызывать реакцию Gizmo, это выясняется испытанием, **не обходом защиты**.
